SMALL QUESTIONS FROM SWEEP65, NONE OF THEM A DEFECT TODAY. Gathered into one order so no shift re-reads them.

1. THE CATALOGUE MERGE CHOSE A BOUND OVER KEEPING EVERY ENTITY (pipeline.write_record_catalogue; run #65 changed which rows survive, not how many). When a duplicated name cannot be paired one to one, the merge carries disk rows forward only until the cast is as large as the disk copy was (max(m, k)). Run #65 made it spend that budget on disk rows whose (name, type, description) the fresh cast does not carry at all, before rows that merely duplicate a fresh one (sweep65 batch03 reproduced a unique entity being dropped for a duplicate). It did NOT make those rows carry unconditionally, because a wiki that rewords the descriptions of a duplicated name would then grow the record by the whole group on every re-catalogue (drill case 6 now pins that bound). The consequence: when a re-catalogue both rewords AND loses an entity inside a duplicated-name group, the lost entity can still be dropped. Should the library (a) keep the bound as it is now, (b) keep every lone row and accept growth under rewording, or (c) keep lone rows but mark them (e.g. `stale_since`) so a curator can prune them?

2. tells.py `_anchor()` (about line 171) slices the first four characters `^\s*` off a pattern and splices `_SENTENCE_START` in its place. Every pattern in the file starts that way today. A future pattern with a different leading anchor would become a broken regex silently. Add an explicit check, or leave it as a convention for a small hand-kept file?
